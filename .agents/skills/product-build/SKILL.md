# Product Build

Execute the approved artifact prepared by [Product Plan](../product-plan/SKILL.md), only after an explicit build request.
Load [the shared product-contract reference](../product-contract/SKILL.md) for source, authority, binding and acceptance invariants.
[The existing build CLI](../../../bin/fm-product-build.py)'s current help owns artifact, ownership, execution, revision and recovery mechanics; use it rather than recreating them in chat or a new scheduler.

## Start or resume the exact approved build

1. Resolve the explicit build identifier and owning parent home, then verify its immutable artifact against current approval through the build interface.
   If none exists, return to Product Plan; do not synthesize approval, silently select another artifact or treat `/product-build` as a waiver of missing decisions.
   Recover an existing exact build from its durable records, never by discovering endpoints across homes.
2. Follow [secondmate provisioning](../secondmate-provisioning/SKILL.md) and [harness adapters](../harness-adapters/SKILL.md) to prepare the dedicated owner, using the build interface's parent reservation and dedicated-home import before project provisioning or implementation launch.
   The build CLI owns the lifetime one-build/one-secondmate binding and the narrow local-only supervision exception; ordinary domain routing and parent landing authority are unchanged.
   The parent routes the approved artifact, not a reconstructed child inventory; the dedicated secondmate owns the rest of this execution sequence in its own home.
3. Bind each exact approved assignment to its generated task instructions through [lifecycle integration](../product-contract/references/lifecycle.md), retaining the approved intent projection and all required checks.
   Prepare the bounded execution plan against the complete approved roster through the build interface; it attempts deferred-start map freshness using [the existing Graphify adapter](../../../bin/fm-product-graph.py).
   Provision that adapter in the dedicated home's prescribed private graph location only under existing pin/install authority; changed code-map inputs never constitute semantic approval.
4. Before any worker allocation, establish and prove the owner-visible private report sink through [the report interface](../../../bin/fm-product-report.py)'s current help.
   The dedicated secondmate's existing local supervision poll owns every-900-second reporting, including unchanged progress and honest overdue recovery; do not add another scheduler or a model-memory reminder.
   Routine reports stay in that sink, not the main firstmate's escalation channel.
   Major failures, required owner input, review/merge calls and final outcomes still use the established parent channel.
   Unsupported or unavailable reporting remains a concrete start blocker, not a hidden-file substitute.

## Execute bounded work and integrate

5. Ask the build interface for the dependency-ready wave, resolve each written task's dispatch profile under normal Firstmate routing, then use its durable dispatch operation through existing launch/capacity admission.
   Start independent slices in parallel when capacity permits; overlapping ordinary files alone are not a reason to serialize.
   Supervise the exact approved direct reports through existing Firstmate supervision and keep the selected delivery path in charge of validation.
6. At a bounded checkpoint or measured context pressure, persist the build interface's handoff with accepted inputs, decisions, commits, artifact/evidence hashes, defects, next action and validation custody.
   Use its supported fresh-context replacement path before repeated compaction, not a resumed conversation presented as a fresh worker.
   Unknown utilization is unknown, not fabricated telemetry; unsupported replacement requires the existing recovery/decision path.
   Reconcile interrupted launch/replacement actions by exact task before retrying; never blindly duplicate workers.
7. The secondmate decides integration but delegates all project edits to the named integration worker.
   Record accepted exact-head integration receipts through the build interface before dependent work starts; refresh maps at integrated wave boundaries and retain all earlier observations.
   Existing ready/landing checks and the approved delivery selection remain authoritative.

## Changes, verification and completion

8. Classify findings through the build interface's change path, using [acceptance authority](../product-contract/references/acceptance.md) and existing ask-user handling rather than letting an implementation worker answer its own finding.
   Its `change`/`act-change` operations own automatic in-scope repair, immutable technical variance, exact parent questions and stopped affected dispatch.
   Product-semantic changes return to Product Plan's exact-source audit/approval sequence, then the parent's successor publication and dedicated owner's revision import; never overwrite an approved manifest or infer new external authority.
9. Apply [the evidence contract](../product-contract/references/evidence.md) at one final integrated candidate, not unrelated slice heads or passing-test totals.
   Use the build interface's repair and finish operations to evaluate the complete accepted requirement/acceptance inventory, attempt the actual final map refresh, repair in-scope failed oracles within current validation custody and reverify the repaired final candidate.
   Missing evidence is unverified, not automatically a defect or a success; real unresolved blockers go to the parent with the exact unmet obligations.
10. Report product acceptance, delivery completion and record reconciliation separately using the retained finish result.
    A demonstrated working product can be called complete with a concise pending-records notice; map/specification/traceability/final-summary debt is cleanup, never a reason to revoke valid behavioral acceptance or waive real product proof.
    The existing finish/report interfaces retain the exact-build change inventory, supersessions and handoffs and retry final report delivery; no receipt is claimed before actual publication.
    Reconcile records automatically in bounded follow-up work and offer a separate cleanup worker when work remains or cannot proceed.
    A later actual behavioral defect reopens acceptance; stale paperwork alone does not.
11. Follow [ship landing](../ship-landing/SKILL.md) for review, authorized landing and cleanup, with parent-owned guarded landing for the dedicated local-only case.
    No build artifact, passing evaluator or secondmate grants publication, merge, destructive or security-sensitive authority.
    Preserve private source, proof, map, change and report history after worker cleanup under [the lifecycle reference](../product-contract/references/lifecycle.md).
